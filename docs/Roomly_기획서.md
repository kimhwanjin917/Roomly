# Roomly 🏨
> 텔레그램 단톡방을 대체하는, 호텔 하우스키핑 실시간 관리 툴

**버전**: v1.25  
**최종 업데이트**: 2026-09-26  
**기술 스택**: Next.js + Supabase + Vercel + Toss Payments

---

## 1. 한 줄 정의

관리자는 객실 현황을 한눈에 보고, 직원은 지금 당장 어느 방을 치워야 할지 바로 안다.

---

## 2. 문제 정의

| 현실 | 문제 |
|------|------|
| 안다즈 같은 5성급 호텔도 텔레그램으로 객실 배정 | 직원이 "지금 어느 방 치워야 해?" 헷갈림 |
| 관리자가 엑셀 정리 후 단톡방에 올림 | 실시간 반영 안 됨, 버전 충돌, 체크인 임박 방 놓침 |
| 기존 Oracle PMS 솔루션은 비싸고 무거움 | 중소형 호텔은 엄두도 못 냄 |

## 3. 타겟 시장

### 1차 타겟 — 알바 중인 대형 호텔
- 안다즈, 신라 등 하우스키핑팀
- 직접 써봤으니 피드백 빠름
- 무료로 제공 후 레퍼런스 확보

### 2차 타겟 — 중소형 모텔·비즈니스호텔
- 객실 20~150개 규모
- 자체 시스템 없이 카톡으로 운영
- 사장님이 바로 결정 → 영업 사이클 짧음
- 전국 수만 곳

## 4. 핵심 기능 (MVP)

### 직원 화면
- 내 배정 방 목록 (체크인 임박 순)
- 체크인 임박 방 빨간색 강조 + 아이콘 병행 (색맹 대응)
- 방 탭 → 청소중 → 완료 원터치
- 특이사항 메모
- QR로 접속 (앱 설치 불필요, 직원별 개인 QR)
- 배정 시 푸시 알림 수신

### 관리자 화면
- 전체 객실 현황판 한눈에 (태블릿/PC 최적화, 모바일 대응)
- 상태별 구분: 더티 / 청소중 / 완료 / 점검대기
- 층별·직원별 필터 뷰
- 방 배정 (직원별 드래그앤드롭)
- 체크인 2시간 전 자동 긴급 표시
- 일일 완료 통계 + 직원별 평균 처리 시간

### 자동화·알림
- 체크아웃 입력 → 즉시 더티 표시, 배정 가능 상태 전환
- 배정 완료 → 해당 직원 화면에 브라우저 푸시 알림
- 체크인 2시간 전 미완료 방 → 관리자 화면 브라우저 푸시 알림
- 직원 완료 처리 → 관리자 화면 실시간 반영 (새로고침 불필요)
- 카카오톡 등 외부 알림 연동은 추후 단계에서 구현

### 인증·접근 방식
- 관리자: 이메일/비밀번호 로그인
- 고정 직원: 개인별 고유 QR 코드 (JWT 영구 세션 토큰 기반 — exp 클레임 없이 발급. qr_version 불일치 시 서버에서 거부)
- 게스트(일일알바): 로그인 없이 일일 접속 코드(6자리)만 입력 → 당일 한정 제한 권한 부여
- 호텔별 데이터 완전 격리 (멀티테넌시)

### 게스트 권한 범위
- 허용: 게스트 풀에 배정된 객실 조회 + 상태 변경 (dirty → cleaning → done → inspect)
- 불가: 전체 객실 현황 조회, 다른 직원 배정 내역 조회, 관리자 기능 일체
- 접속 코드는 관리자가 매일 발급, 당일 자정 만료

## 4-1. 하우스키핑 에이전트

### 왜 에이전트인가

배정은 한 번 계산하고 끝나는 최적화 문제가 아니다. 하루 종일 전제가 바뀐다.

- 체크아웃이 예정보다 늦게 난다
- 직원이 지각하거나 결근한다
- 청소가 예상보다 오래 걸린다
- 체크인이 앞당겨진다

관리자가 실제로 하는 일은 계속 **관찰 → 재판단 → 개입**이다. 프롬프트를 한 번 쏘고
추천 목록을 받는 방식은 30분 뒤면 무의미해진다. 그래서 루프로 만들었다.

### 루프

```
5분마다 (api/cron/agent)
   ↓
관찰   get_board / get_staff_performance     ← 모델이 도구로 직접 조회
   ↓
계획   배정안 산출
   ↓
검증   validate_plan → 위반 시 사유를 tool_result로 반환 → 재생성 (최대 3회)
   ↓
실행   assign_rooms (실제 배정 + 직원 푸시)
   ↓
기록   agent_logs에 판단 근거와 예측 완료 시각 저장
```

### 도구 4개

| 도구 | 하는 일 | 재사용한 기존 코드 |
|------|---------|--------------------|
| `get_board` | 현황판 조회 (urgent 판정, 예상 소요 시간 포함) | `lib/rooms.ts` |
| `get_staff_performance` | 직원별 7일 실적과 현재 작업량 | `lib/reports.ts` |
| `assign_rooms` | 검증 통과 시 실제 배정 + 푸시 발송 | `api/admin/assign` |
| `alert_admin` | 사람이 개입해야 할 상황을 관리자에게 알림 | `lib/push.ts` |

새로 만든 업무 로직은 없다. 관리자 버튼에만 연결돼 있던 기능을 모델도
호출할 수 있게 노출한 것이다.

### 결과 검증 (3층)

1. **구조** — 모델이 지어낸 객실/직원 ID를 실제 목록과 대조해 거부
2. **규칙** — `lib/agent-validate.ts`
   - 한 객실을 두 명에게 배정
   - 체크인 임박 객실 누락 (가장 치명적)
   - 특정 직원에게 예상 작업량 쏠림 (균등 분배 + 60분 초과)
   - 배정 가능한데 빈 계획 제출
3. **사후** — 배정 시 예측 완료 시각을 `agent_logs.detail`에 남기고 실제 완료 시각과 대조

검증 위반은 예외로 던지지 않고 **문장으로 모델에게 돌려준다.** 모델은 사유를 읽고
같은 루프 안에서 계획을 고친다. 3회 연속 거부되면 포기하고 관리자를 부른다.

### 투명성

관리자 대시보드의 `에이전트` 패널이 활동 로그를 보여준다.
**검증에서 거부된 계획도 숨기지 않는다** — 에이전트가 스스로 되돌린 흔적이 보여야
관리자가 어디까지 맡길지 판단할 수 있다.

```
14:32  ✓ 302호 → 김민지 · 체크인 1시간 20분 전, 같은 층
14:32  ⟲ 배정안 거부 (1/3) — 405호는 체크인이 임박했는데 배정되지 않았습니다
14:31  ◎ 현황판 조회 — 배정 대상 7개 (더티 7, 청소중 3, 완료 30)
```

### 성능 비교

`scripts/replay.mjs`가 같은 하루 시나리오를 규칙 기반(체크인순 순환 배정)과
에이전트로 각각 돌려 비교한다. 제품 기능이 아니라 1회성 분석 스크립트다.

```
node scripts/replay.mjs --check    # 검증 규칙 자체 점검
node scripts/replay.mjs            # 두 전략 비교 (ANTHROPIC_API_KEY 필요)
```

| 지표 | 규칙 기반 | 에이전트 | |
|------|-----------|----------|---|
| 체크인 초과 | 3건 (209·503·505호) | **0건** | 전부 해소 |

직원별 총 작업 시간:

| | 김민지 | 박서준 | 이하늘 | 정우성 |
|---|-------|-------|-------|-------|
| 규칙 기반 | 494분 | 300분 | 226분 | 75분 |
| 에이전트 | 353분 | 290분 | 249분 | 230분 |

규칙 기반(체크인순 순환 배정)은 객실 소요 시간과 직원 숙련도를 모르기 때문에
한 명에게 494분이 쏠리는 동안 다른 한 명은 75분만 일한다. 6.6배 차이다.
에이전트는 230~353분, 1.5배 이내로 맞춘다.

검증 루프는 이 실행에서 한 번도 거부를 내지 않았다 — 모델의 1차 계획이
매번 규칙을 통과했다. 검증 자체의 동작은 `--check`의 규칙 테스트 6종으로 확인한다.

> 아직 실사용 호텔이 없어 과거 로그가 없다. 비교는 시드 시나리오 기반
> **시뮬레이션**이며, 실제 운영 결과가 아니다.

## 5. 기술 스택

| 기술 | 선택 이유 |
|------|-----------|
| Next.js 14 | React 기반 풀스택. App Router로 관리자/직원 페이지 분리. Vercel 배포 최적화 |
| Supabase | PostgreSQL 기반 실시간 DB. 관계형 데이터 구조에 최적. 인증 내장. 무료 플랜 넉넉 |
| Vercel | Next.js 만든 회사. 배포 1분. 무료 플랜으로 MVP까지 비용 0원 |
| PWA | 앱 설치 없이 QR 찍으면 폰에서 바로 실행. 오프라인 시 마지막 배정 목록 캐시 유지 |
| Tailwind CSS | 빠른 UI 개발. 모바일 반응형 쉽게 구현 |
| Toss Payments | 국내 카드 결제 + 정기 빌링키. 중소 사업자 대상 SaaS에 적합 |
| Capacitor | PWA를 iOS/Android 네이티브 앱으로 래핑. 스토어 배포 + FCM 푸시 지원 |
| next-intl | 다국어 지원 (한국어/영어/베트남어). 직원 화면 현지화 |

## 6. DB 구조

```sql
-- 호텔 정보
hotels (id, name, subscription_plan, created_at,
        stripe_customer_id, stripe_subscription_id, plan_expires_at)
-- total_rooms 제거: rooms 테이블 COUNT로 대체 (동기화 문제 방지)
-- subscription_plan: 'starter' | 'standard' | 'pro'

-- 객실 상태 관리
rooms (id, hotel_id, number, floor, type, status, checkin_time, deleted_at)
-- floor: 층별 배정 단위
-- type: single | double | suite 등 (청소 소요 시간 다름)
-- deleted_at: 소프트 삭제 컬럼. NULL = 활성. 물리 삭제 금지. 모든 조회에 WHERE deleted_at IS NULL 필수
-- priority 컬럼 없음: ORDER BY checkin_time ASC NULLS LAST 쿼리로 대체 (저장 불필요)

-- 직원 정보 (worker 전용 — 관리자는 Supabase Auth app_metadata로만 관리, staff row 없음)
staff (id, hotel_id, name, auth_id, phone_number, qr_version)
-- auth_id: 직원 등록 시 서버가 생성한 UUID. Supabase Auth 계정이 아님.
--          커스텀 QR JWT의 sub 클레임으로 사용 → auth.uid()와 매칭되어 RLS "직원 본인 조회" 동작
-- phone_number: 추후 외부 알림 연동 시 사용
-- qr_version: QR 재발급 시 1씩 증가. JWT에 포함해 구 QR 무효화에 사용 (기본값 1)

-- 배정 이력
assignments (id, room_id, staff_id, is_guest, assigned_at, completed_at, cancelled_at)
-- staff_id: 게스트 배정 시 NULL
-- is_guest: true면 게스트 풀 배정
-- completed_at: 청소 완료 시각 (직원별 평균 처리 시간 집계)
-- cancelled_at: 재배정으로 취소된 시각 (completed_at과 의미 분리)

-- 게스트 접속 코드
guest_codes (id, hotel_id, code, date, expires_at, created_at)
-- code: 6자리 랜덤 코드, 당일 자정 만료
-- date: 코드가 유효한 날짜 (KST). UPSERT ON CONFLICT (hotel_id, date) 기준 컬럼

-- 라이선스 키 (가입 시 검증)
licenses (id, key, created_at, used_at, hotel_id)

-- 브라우저 푸시 알림 구독
push_subscriptions (id, staff_id, hotel_id, is_admin, endpoint, p256dh, auth, created_at)

-- 에이전트 활동 로그
agent_logs (id, hotel_id, cycle_id, kind, message, detail, created_at)
-- cycle_id: 한 번의 실행(관찰→계획→검증→실행)에 속한 로그를 묶는 키
-- kind: observe | plan | reject | assign | alert | error
--       reject = 검증에서 되돌린 계획. 숨기지 않고 관리자에게 그대로 노출한다
-- detail: 도구 입출력 원본. assign일 때 예측 완료 시각을 담아 사후 검증에 쓴다
-- 정책 없음 = service role 전용 (payment_logs, email_logs와 동일)

-- 상태 변경 이력
room_logs (id, room_id, status, changed_by, changed_at, memo, alert_type)
-- changed_by: staff.id (고정 직원/관리자) 또는 'guest' 문자열 (게스트 변경 시)
-- alert_type: NULL(알림 없음) | 'urgent_2h'(체크인 2시간 전 알림 발송) | 'overdue'(체크인 초과 알림 발송)
--             두 알림 타입을 분리해 중복 발송을 각각 독립적으로 방지
```

### 객실 상태값
- `dirty` — 더티 (청소 필요)
- `cleaning` — 청소중
- `done` — 완료
- `inspect` — 점검 대기

## 7. 개발 로드맵

### 호텔 가입 방식
- **현재 (라이선스 기반 셀프 가입)**: 운영자가 `/super-admin`에서 라이선스 키 발급 → 호텔이 `/signup`에서 키 입력 후 셀프 가입
- **추후**: 라이선스 없이 카드 등록만으로 즉시 가입 (Stripe 완전 자동화 후)

### 1단계 — 프로토타입 ✅ 완료 (2026-06-22)
- 객실 현황판 UI (층별 뷰, 실시간 반영)
- 상태 변경 + 실시간 반영 (Supabase Realtime)
- QR 기반 직원 인증 + 게스트 코드 인증
- PWA (홈 화면 설치, 오프라인 캐시)
- 온보딩 마법사, 라이선스 기반 가입
- 슈퍼어드민 대시보드 (`/super-admin`)
- 랜딩 페이지 (`/`)

### 2단계 — MVP 출시 🚧 진행 중
- ✅ 푸시 알림 인프라 (VAPID Web Push, push_subscriptions)
- ✅ Toss Payments 결제 기반 세팅 (checkout, webhook, 빌링키 정기결제)
- ✅ Resend 이메일 (가입 환영 메일)
- ✅ 직원 화면 다국어 (한/EN/VI, next-intl)
- ✅ 배정 드래그앤드롭 (@dnd-kit)
- ✅ Capacitor 네이티브 앱 구조 (android/, ios/)
- ✅ 하우스키핑 에이전트 (도구 호출 + 검증 루프, 5분 크론) — 4-1 참고
- 🔲 결제 라이브 상점 심사 + 빌링키 계약
- 🔲 결제 플랜 만료 잠금
- 🔲 일일 리포트 이메일 크론
- 🔲 통계 주간/월간 차트
- 🔲 Rate Limiting (Upstash Redis)

### 3단계 — 정식 서비스
- PMS 연동 + 다국어(영어·베트남어) + 체인 호텔 관리
