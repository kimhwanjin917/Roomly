# Roomly 에러 케이스 정의

> 예외 상황별 처리 방식 정의. AI가 임의로 판단하지 않도록 사전 명세.

---

## 인증 관련

| 케이스 | 상황 | 처리 방식 |
|--------|------|-----------|
| AUTH-01 | 관리자 로그인 실패 (이메일/비밀번호 틀림) | "이메일 또는 비밀번호가 올바르지 않습니다" 표시. 계정 잠금 없음 |
| AUTH-02 | 비로그인 상태로 `/admin` 접근 | `/login`으로 리다이렉트 |
| AUTH-03 | 직원 QR 링크 무효 | "접속 링크가 올바르지 않습니다. 관리자에게 문의하세요" 표시 |
| AUTH-04 | 직원이 타인의 `/worker/[staffId]` 접근 | 403 처리 → "접근 권한이 없습니다" 표시 |
| AUTH-05 | 세션 만료 중 관리자가 작업 중 | 다음 API 요청 시 `/login`으로 리다이렉트. 작업 중 데이터는 유실 |
| AUTH-06 | 게스트 코드 틀림 | "코드가 올바르지 않습니다" 표시. 재입력 가능. 잠금 없음 |
| AUTH-07 | 게스트 코드 만료 (당일 자정 이후) | "오늘의 코드가 만료되었습니다. 관리자에게 문의하세요" 표시 |
| AUTH-08 | 게스트 세션 만료 후 `/worker/guest` 접근 | 세션 쿠키에 저장된 hotelId로 `/guest?h={hotelId}` 리다이렉트. hotelId 없으면 `/guest`로 리다이렉트 |
| AUTH-11 | `/guest` 접근 시 `?h` 파라미터 없음 | "잘못된 접속 링크입니다. 관리자에게 접속 URL을 다시 받으세요" 표시. 코드 입력 폼 비활성화 |
| AUTH-09 | 게스트가 `/admin` 또는 `/worker/[id]` 접근 시도 | 403 처리 → "접근 권한이 없습니다" 표시 |
| AUTH-10 | QR 재발급 후 구 QR로 접속 | 구 JWT는 서버에서 `staff.qr_version` 클레임과 비교해 불일치 시 거부 → "QR이 만료되었습니다. 새 QR을 사용하세요" 표시. (재발급 시 `staff.qr_version` 값을 1 증가시키고 새 JWT에 해당 버전 포함) |

## 객실 상태 관련

| 케이스 | 상황 | 처리 방식 |
|--------|------|-----------|
| ROOM-01 | 이미 `cleaning` 상태인 방을 다른 직원이 [청소 시작] 탭 | RLS에서 차단됨 (배정되지 않은 방). 화면에 "배정된 방이 아닙니다" 토스트 표시 |
| ROOM-02 | 체크인 시간이 이미 지났는데 `dirty` 상태 | 긴급 표시 유지 + 관리자에게 "체크인 시간 초과 미완료" 브라우저 푸시 알림 발송 (2시간 전 알림과 별개). 트리거: 클라이언트 60초 폴링으로 감지. 이후 추가 알림 없음 (room_logs.alert_type = 'overdue' 존재 여부로 중복 방지) |
| ROOM-03 | `done` 상태 방을 다시 `dirty`로 변경 | 관리자만 가능. room_logs에 변경 이력 기록 |
| ROOM-04 | `inspect` 상태에서 직원이 완료 처리 시도 | 직원 화면에서 [완료] 버튼 비활성화. "관리자 점검 후 처리됩니다" 안내 |

## 배정 관련

| 케이스 | 상황 | 처리 방식 |
|--------|------|-----------|
| ASSIGN-01 | 이미 배정된 방에 다른 직원을 재배정 | 기존 assignments row의 cancelled_at에 취소 시각 기록 후 새 row 생성 (completed_at은 청소 완료 전용, 의미 분리). 기존 직원 화면에서 해당 방 사라짐 |
| ASSIGN-02 | 직원 없이 배정 시도 (드롭다운 미선택) | "직원을 선택해주세요" 표시. 저장 불가 |
| ASSIGN-03 | 직원 삭제 시도 (미완료 배정 있음) | `DELETE /api/admin/staff/[id]` → 409 반환. 클라이언트에서 "미완료 배정이 N건 있습니다. 그래도 삭제하시겠습니까?" 다이얼로그 표시. 확인 시 `?force=true`로 재요청 → 미완료 assignments.cancelled_at 일괄 기록 후 staff row 삭제 (직원은 Supabase Auth 계정 없음). 삭제 후 현황판에 해당 방 "미배정"으로 표시 |
| ASSIGN-04 | 게스트 접속 시 게스트 풀에 배정된 방이 없음 | "아직 배정된 방이 없습니다. 관리자에게 문의하세요" 표시. 목록 빈 상태로 대기 |
| ASSIGN-05 | 고정 직원이 배정된 방 없이 접속 | "아직 배정된 방이 없습니다." 표시. 목록 빈 상태로 대기. 배정 시 실시간 반영 |
| ASSIGN-06 | 당일 게스트 코드 중복 발급 | 기존 당일 코드를 새 코드로 덮어씀 (guest_codes에서 hotel_id + 당일 row 업데이트). 이전 코드로 발급된 세션은 유지됨 (JWT 만료 전까지) |

## 알림 관련

| 케이스 | 상황 | 처리 방식 |
|--------|------|-----------|
| NOTIFY-01 | 브라우저 푸시 알림 권한 거부 | 알림 권한 없어도 서비스 정상 동작. 배정 목록은 화면에서 항상 확인 가능. 권한 요청 배너만 1회 표시 |
| NOTIFY-02 | 직원이 브라우저를 닫은 상태에서 배정 | 푸시 알림 미수신. 다음 접속 시 배정 목록에서 자동 확인 가능. 별도 처리 불필요 |
| NOTIFY-03 | 긴급 알림 중복 발송 방지 | room_logs의 `alert_type`으로 구분. 발송 전 `SELECT 1 FROM room_logs WHERE room_id = ? AND alert_type = ?` 조회. 이미 있으면 스킵. `'urgent_2h'`와 `'overdue'`는 독립적으로 체크해 각각 최대 1회만 발송 |

## 네트워크 / 실시간 관련

| 케이스 | 상황 | 처리 방식 |
|--------|------|-----------|
| NET-01 | 직원 화면 오프라인 | PWA 캐시로 마지막 배정 목록 표시. 상태 변경 버튼 비활성화. "오프라인" 배너 표시 |
| NET-02 | Supabase Realtime 연결 끊김 | 자동 재연결 시도 (Supabase 클라이언트 기본 동작). 재연결 중 "연결 중..." 배너 표시 |
| NET-03 | 동시에 두 명이 같은 방 상태 변경 | DB 업데이트는 마지막 요청이 반영됨. Realtime으로 양쪽 화면 모두 최신 상태로 동기화 |

## 데이터 관련

| 케이스 | 상황 | 처리 방식 |
|--------|------|-----------|
| DATA-01 | 체크인 시간 미입력 방 | 긴급 표시 제외. 우선순위 최하단. 관리자가 직접 입력하도록 유도 |
| DATA-02 | 직원 전화번호 미입력 | 저장은 가능. 브라우저 푸시 알림에는 영향 없음. 추후 외부 알림 연동 시 발송 대상에서 제외됨 |
| DATA-03 | 객실 수 0개인 호텔 | 현황판에 "등록된 객실이 없습니다. 객실을 추가해주세요" 안내 표시 |
